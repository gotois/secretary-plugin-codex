# Guided task intake

Для новой задачи готовь проверенный редактируемый draft; существующую задачу
изменяй через `edit`, сохраняя её ID. Используй
Secretary MCP для приватных данных и controlled actions; skill не является
слоем authorization или validation.

## Workflow

1. Определи намерение: создать, изменить, получить совет либо уточнить действие.
2. Извлеки `name`, `description`, `start_date`, `end_date`,
   `estimated_unix_time`, `id_category`, `priority`, `location`,
   `link_meeting` и `id_cal_class`.
3. Безопасно дополни draft контекстом. Задай один вопрос, только если действие,
   дата, конфликт или совпадение существующих задач существенно неоднозначны.
4. Для изменения переходи к «Изменение существующей задачи» и заверши эту ветку
   без перехода к созданию. Для совета не готовь draft, пока пользователь не
   попросит запланировать результат.

## Создание новой задачи

1. Выбери `id_category` через `$task-categorization`; не выдумывай категории.
2. Определи дату, часовой пояс и длительность до проверки доступности. Если
   время не задано, предложи его или уточни; не позволяй серверному значению
   по умолчанию молча назначить задачу на текущий момент.
3. Вызови `list-calendar-tasks` на день и `check-availability` на точный интервал.
   Для задачи через полночь прочитай все затронутые дни. При пересечении с
   задачей, BUSY или BUSY-UNAVAILABLE предложи другое время и повтори проверки;
   BUSY-TENTATIVE явно согласуй с пользователем.
4. После проверок вызови `prepare-create-form`: это model-facing draft step и
   он не пишет в БД.
5. Покажи draft обычным языком: title, category, дату, время, duration,
   priority и допущения. Остановись для edit/confirm/reject. Никогда не вызывай
   `create`: существующий UI делает это только после явного подтверждения.
   Если форма недоступна в текущем host, объясни ограничение и направь
   пользователя в Secretary UI; текстовое подтверждение не заменяет вызов из UI.

## Изменение существующей задачи

1. Прочитай исходную задачу через `list-calendar-tasks` за подходящий период.
   Если совпадений несколько или задача не найдена, уточни выбор. Используй
   только возвращённый `id_task`; не заменяй отсутствие задачи созданием новой.
2. Подготовь только запрошенные изменения по актуальной схеме `edit`. Сохрани
   текущий `id_tasks_status` и передай его явно: сервер иначе подставляет статус
   по умолчанию. Не перекатегоризируй задачу при обычном переносе.
3. При переносе сохрани длительность, если пользователь не просил её изменить,
   и передай согласованные `start_date` и `end_date` явно. Проверь задачи за все
   затронутые дни и `check-availability` на новый интервал. В списке задач исключи
   из сравнения только исходный `id_task`; не игнорируй busy-интервалы без
   известного источника. Разреши конфликты по правилам создания выше. При правке
   только текста не требуй нового свободного слота.
4. Покажи, что изменится. Явный запрос пользователя на конкретную правку уже
   разрешает её; если предлагаешь другое время или дополнительные изменения,
   получи согласие на них перед записью.
5. Вызови `edit` с исходным `id_task`, текущим статусом и согласованными полями.
   Этот инструмент сразу изменяет задачу. Не вызывай `prepare-create-form` или
   `create` для изменения и не удаляй исходную задачу ради переноса.
6. Сообщи об успехе только после успешного ответа `edit` для того же `id_task`.
   Если `edit` недоступен, объясни ограничение и предложи изменить задачу в UI.

## Guardrails

- Не утверждай, что задача создана, пока `create` не завершится успешно.
- Не скрывай conflicts или tool errors; не показывай технический JSON без пользы.
- Не используй таблицу для одного draft и не создавай подзадачи без подтверждения.
- Не переноси authorization, ownership, ID/range validation и работу с secrets в
  model reasoning.

## Failure handling

Если чтение или подготовка draft завершились ошибкой, назови неудавшийся шаг,
сохрани известные параметры и не переходи к записи. При отклонении draft
подтверди, что ничего не создано.

При ошибке `edit` не переходи к созданию. Если ответ потерян или произошёл
таймаут, сначала перечитай задачу: запись могла пройти. Не повторяй изменение
вслепую и не утверждай, что ничего не изменилось, пока результат неизвестен.
